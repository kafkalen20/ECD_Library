# SEC-6 개인정보 가림 중복 처리 검토

> 작업목록: `공통보안모듈_작업목록_261105.xlsx` → `기존 모듈 보완` 시트 SEC-6 (P2)
> 기준 코드: `feature/edb-security-merge` 커밋 `5ecd47f` (PR #1). 줄 번호는 이 커밋 기준이다.
> **결론 먼저: 리뷰에서 말한 문제(잘림 표시가 덮임)는 실행해 보니 재현되지 않았다. 이 항목은 2026-11-17 종결했다.** 대신 확인 중에 다른 가림 누락 1건을 찾아 아래에 적었다.

## 배경 / 목표 (무엇을 왜)

보안 이벤트의 `detail`·`field_names`는 저장 전에 개인정보 패턴(주민번호·이메일·전화·계좌)을 가린다 (`core/masking.py`). 가림은 두 곳에서 실행된다.

1. `collector.record()` (`core/collector.py:76, 78`): 분리 커넥션(raw SQL) 경로가 ORM `create()`를 타지 않아서, 분기 전에 가린다.
2. `edb.security.event.create()` (`models/security_event.py:78, 80`): ORM으로 만드는 모든 경로를 막기 위해 가린다. `collector`를 거치지 않는 호출(예: `_log_toggle_change`)도 여기서 가려진다.

ORM 경로로 들어온 값은 1과 2를 둘 다 거친다. 리뷰에서는 "4000자를 넘는 값은 두 번째 가림에서 잘림 표시(`…(truncated)`)가 덮인다"고 보았다.

## 확인 결과 (2026-11-16, `masking.mask`를 직접 두 번 실행)

| 입력 | 1번 가림 길이 | 2번 가림 길이 | 결과 같음 |
|---|---|---|---|
| `a` × 5000 | 4012 | 4012 | 같음 |
| 3990자 + 이메일 + 100자 | 4012 | 4012 | 같음 |
| `연락처 010-1234-5678 ` × 300 | 3600 | 3600 | 같음 |
| `z` × 3995 + `010-1234-5678` | 4012 | 4012 | 같음 |

- 이유: 첫 번째 가림의 결과는 "4000자 + 잘림 표시"다. 두 번째 가림은 다시 앞 4000자를 자르고 같은 잘림 표시를 붙이므로 결과가 같다. 가림 토큰(`[EMAIL]` 등)에는 숫자·@가 없어 다시 걸리지 않는다.
- 즉 **두 번 실행해도 결과는 같다(멱등).** 같은 일을 두 번 하는 비용만 있는데, 문자열 정규식 5개라 무시할 수준이다.

**두 곳 중 하나를 지우면 안 된다**: 1을 지우면 분리 커넥션 경로가 가려지지 않고, 2를 지우면 `collector`를 거치지 않는 ORM 호출이 가려지지 않는다. 지금 구조가 맞다.

## 확인 중 찾은 다른 문제 (별도 항목 후보)

위 4번째 입력에서 전화번호 `010-1234-5678`이 **가려지지 않았다** (`zzzz…010-1…(truncated)`로 남음).

- 원인: 패턴이 `\b`(단어 경계)로 시작한다 (`masking.py:13-20`). 숫자 바로 앞에 영문자·숫자·밑줄이 붙어 있으면 경계가 아니라서 걸리지 않는다. 예: `tel010-1234-5678`, `ID_9001011234567`.
- 이것은 README B6 "Phase 2 선행 조건 1"(가림 패턴 보강)과 같은 범주다. 그 작업에 이 사례를 넣는 것을 제안한다.

## 대안 검토 (택하지 않은 방향)

- **`create()`에서 가림을 빼고 `collector`에만 두기**: `collector`를 거치지 않는 ORM 호출이 가려지지 않는다.
- **이미 가렸다는 표시(컨텍스트 키)를 넘겨 두 번째를 건너뛰기**: 표시를 위조하거나 빠뜨리면 가림이 빠진다. 아끼는 비용에 비해 위험이 크다.
